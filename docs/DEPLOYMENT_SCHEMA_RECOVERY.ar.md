# حماية النشر بعد ترقية قاعدة البيانات

عند تعثر فحص الجاهزية بعد نشر إصدار يرقّي قاعدة البيانات، كان المسار السابق يعيد ملفات البرنامج القديم فقط. إذا رُقّيت القاعدة بالفعل من 52 إلى 53، يرفض البرنامج الأقدم التشغيل برسالة `Database schema version 53 is newer than this application`. هذه مشكلة في تعافي النشر، وليست دليل تلف بيانات.

استُعيد التشغيل بتثبيت البرنامج الحديث المتوافق مع القاعدة الحالية، دون استعادة نسخة مالية قديمة أو خفض إصدار القاعدة. جرى التحقق من جاهزية API، وتطابق الملفات المثبتة، وعمل خدمات API والوكيل والنفق، وإرجاع الدومين صفحة التطبيق وأصول الإصدار نفسه، ونتيجة `PRAGMA quick_check = ok`.

حُسّن النشر كما يلي:

- قراءة إصدار القاعدة قبل أي إيقاف أو استبدال، وبعد فشل النشر وقبل محاولة الرجوع. القراءة عبر SQLite بوضع `readOnly`، وليست عبر كود التطبيق الذي قد يشغّل الهجرات.
- إذا تقدم الإصدار، يُمنع الرجوع الآلي إلى ملفات البرنامج القديم؛ تُحفظ الملفات الجديدة والسابقة ويُعرض تشخيص يطلب إصلاحًا إلى الأمام. لا تُستعاد قاعدة بيانات أقدم تلقائيًا.
- إذا تعذرت قراءة الإصدار قبل النشر، يتوقف دون تغيير الخدمات؛ وإذا تعذرت القراءة عند التعافي، لا يجازف باستبدال الملفات.
- تبقى استعادة الملفات العادية كما كانت عندما لا يتقدم إصدار القاعدة.
- زادت مهلة الجاهزية من 30 إلى 90 ثانية للسماح بإقلاع أبطأ. لا تثبت هذه الزيادة وحدها سبب انتهاء المهلة الأولى؛ المؤكد من السجل هو عدم توافق البرنامج القديم مع القاعدة 53 بعد التعافي.

اجتاز اختبار النشر 11 سيناريو محاكاة، إضافة إلى اختبار SQLite فعلي يثبت قراءة الإصدار من مسارات فيها مسافات دون تغير بصمة ملف القاعدة. نجحت الاختبارات على Windows PowerShell 5.1، وأضيفت إلى CI. لا تتعامل المحاكاة مع خدمات الجهاز أو بيانات الإنتاج.
