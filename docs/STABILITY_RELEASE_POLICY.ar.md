# إجراء الاستقرار والنشر

الهدف تقليل أخطاء الموقع والتطبيق واكتشافها مبكرًا، وليس الادعاء بأن أي برنامج يخلو من الأخطاء دائمًا.

## قبل الرفع والنشر

1. تعديل صغير واضح، واختبارات للخلل نفسه، مع إبقاء المنطق المشترك في وحدات مستقلة.
2. تشغيل `npm run verify:release`. الأمر يبني الموقع والخادم ويفحص جودة الكود، ثم اختبارات الحسابات وعقد API، وتكرار الحفظ وفقدان الرد، ومزامنة السجل والإشعارات، واستعادة نسخة تجريبية، وفشل النشر والتراجع عنه.
3. كل هذه الاختبارات تستخدم قواعد بيانات مصطنعة وخوادم اختبار منفصلة. لا تحتاج كلمات مرور staging ولا حسابات الإنتاج، ولا تختبر بالدفع الفعلي.
4. اختبار أي تعديل في عقد API مع نسخة Android المستخدمة على staging قبل الاعتماد المالي. اختبار الخادم الآلي لا يغني عن تجربة APK الفعلي على جهاز Android عند تغيير التطبيق أو عقد الربط.
5. عند نجاح الفحص يُحفظ تقرير `var/release-verification/latest.json`، وفيه الكوميت وبصمة ملفات المصدر وبصمة ملفات الواجهة والخادم ونتيجة كل خطوة. أي فشل يبطل التقرير الناجح السابق.

## أمر السيرفر بعد رفع التعديلات

داخل PowerShell كمسؤول:

```powershell
& {
$ErrorActionPreference = 'Stop'
Set-Location 'C:\Users\Administrator\Desktop\wep-erp-support'

git pull --ff-only origin main
if ($LASTEXITCODE) { throw 'فشل السحب' }

npm.cmd run verify:release
if ($LASTEXITCODE) { throw 'فشل فحص الاستقرار؛ لم يتم نشر التحديث' }

& '.\scripts\deploy-and-verify-admin.ps1' -SourceRoot (Get-Location).Path
}
```

إذا تغيّر ملف المتطلبات أو ملف القفل، تُثبّت المتطلبات المتوافقة أولًا قبل الفحص. لا يلزم إعادة تثبيتها لكل تعديل شكلي.

تُنفّذ الأوامر داخل كتلة واحدة حتى يوقف فشل السحب أو الفحص بقية الخطوات، حتى عند لصقها في جلسة PowerShell تفاعلية. تحفظ كل خطوة مخرجاتها في `var/release-verification/checks`، ويسجل التقرير اسم الخطوة الفاشلة ومسار سجلها. عند الفشل تُراجع التفاصيل بدل تجاوز الفحص أو إعادة تشغيل النشر يدويًا.

أمر النشر المعتمد يرفض التقرير المفقود أو الناقص، أو تغيّر المصدر/الملفات المبنية بعد الفحص، أو وجود تغييرات غير محفوظة في Git، وذلك قبل إيقاف خدمات الموقع. بناء الملفات مرة أخرى بعد اكتمال الفحص قد يغيّر البصمة؛ أعد الفحص بدل الاعتماد على التقرير القديم.

يظل `deploy-built-admin.ps1` أداة داخلية منخفضة المستوى للاستعادة/الإصلاح الإداري، وليس أمر النشر المعتاد. تجاوز الأمر المعتمد يتجاوز فحص تقرير الاستقرار؛ لم يُضف قيد للنشر إلى برنامج الخادم نفسه.

## بعد النشر

- التحقق من جاهزية API بحالة `ready`، وتشغيل الخدمات، ومطابقة ملفات الواجهة والخادم؛ ثم مطابقة كوميت الخادم العامل مع النسخة المفحوصة وخلو بنائها من تغييرات محلية.
- آلية التراجع الحالية تبقي البرنامج السابق. لا تُستعاد قاعدة بيانات قديمة تلقائيًا لإصلاح عطل برنامج، لأن ذلك قد يفقد معاملات جديدة.
- إذا تقدّم مخطط قاعدة البيانات، تُمنع العودة التلقائية لبرنامج قديم غير متوافق، وتُحفظ ملفات الاستعادة للإصلاح إلى الأمام.
- اختبار الاستعادة يجري في الفحص الآلي على بيانات مصطنعة. لم تُغيّر وجهة النسخ الاحتياطية، ولم تُضف نسخًا خارج الجهاز أو تغييرات RDP/VPN.

## المتابعة

تُستخدم أدوات مركز التشغيل الموجودة لمتابعة أخطاء الخادم وحالة قاعدة البيانات والنسخ الاحتياطية، وقياسات الطلبات لتحديد البطء. عند بلاغ موظف يُسجّل الوقت والقسم والعملية ورقم الخطأ إن ظهر، ثم يُعاد إنتاجه على بيانات اختبار ويُضاف اختبار يمنع رجوعه.

فحص GitHub الرئيسي يشغّل نفس بوابة الاستقرار ويحفظ تقريرها. يلزم جعل حالة الفحص مطلوبة في قواعد فرع `main` إذا أُريد منع الدمج من GitHub نفسه؛ تعديل workflow وحده لا يضبط صلاحيات الفرع أو يمنع مالك المستودع من تجاوزه. لم تتغير إعدادات حماية المستودع ضمن هذا التعديل.

اختبار API الحالي يثبّت عقد الإصدار 1: كوكي `abdo_session`، ورمز CSRF، ومصدر المستخدم والصلاحيات `/api/me`، والمبالغ الصحيحة، وعمليات الأقسام الأربعة المستقلة، ومنع تكرار نفس الطلب، وتعارض النسخ، وإبطال الجلسة بعد الخروج. تغيير هذه القواعد يتطلب تنسيقًا مع مطور التطبيق قبل النشر.
