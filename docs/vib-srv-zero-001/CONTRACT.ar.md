# عقد مراجعة الكارت الصفري — VIB-SRV-ZERO-001

هذا العقد مأخوذ من مصدر هذا المستودع بعد التنفيذ، لا من وثائق التطبيق المحمول. لم يُنشر الخادم، ولم تُشغَّل الترقية على قاعدة إنتاج أو تجريب حية، ولا يُعد أي رصيد معتمدًا ماليًا.

## ما يحتويه هذا المستودع

`wep-erp-support` هو مصدر الموقع والخادم معًا: واجهة React وخادم Node.js على HTTP، وSQLite هو مصدر الحقيقة. الحسابات الدائمة للأقسام الأربعة صفوف في `customers` بمفتاح القسم:

| القسم | `section_key` | مسار القائمة والكارت | مسار المراجعة |
|---|---|---|---|
| ديون العملاء | `customer_debts` | `/api/customers` | `POST /api/customers/{id}/zero-review` |
| ديون الشركات | `company_debts` | `/api/companies` | `POST /api/companies/{id}/zero-review` |
| الأمانات الليبية | `libyan_deposits` | `/api/libyan-deposits` | `POST /api/libyan-deposits/{id}/zero-review` |
| الأمانات المصرية | `egyptian_deposits` | `/api/egyptian-deposits` | `POST /api/egyptian-deposits/{id}/zero-review` |

قبل هذا التغيير كانت المراجعة الدائمة موجودة للعملاء فقط. القوائم الثلاث الأخرى كانت تقدر ترجع `summary.pendingReviewCount` وتقبل `filter=pending-review` في المعامل، لكن الشرط كان يحصر الانتظار في `customer_debts`، و`zeroReview` لا يُعاد لغير العملاء، ولا يوجد مسار كتابة لها. هذا ما أصلحه الخادم.

## حالة الكارت

`zeroReview` يُعاد لكل حساب غير مرتبط بنظام داخل الأقسام الأربعة. الحساب ذو `systemLinkKey` لا يحمل `zeroReview` ولا يُراجع.

```json
"zeroReview": {
  "pending": true,
  "financialVersion": 2,
  "reviewedAt": null,
  "reviewedByName": null
}
```

- `pending: true` مع `balanceUnits: 0`: الكارت في المجموعة العليا، والتأكيد مسموح لمن يملك صلاحية القسم.
- `pending: false` مع `reviewedAt` غير فارغ: تمت المراجعة، وينزل إلى مجموعة الأصفار.
- `pending: false` مع `reviewedAt: null`: صفر تاريخي أو رصيد غير صفري. لا تعرض علامة التأكيد.
- `financialVersion` نسخة حركة مالية مستقلة عن `version` الخاصة بتعديل الحساب والحركات. التأكيد يرسل `financialVersion` فقط.

الحالة محفوظة على صف الحساب داخل المؤسسة، لا على الجهاز ولا على الجلسة. `zero_reviewed_by` يسجل المستخدم الذي أكد. أي قراءة لاحقة للحساب نفسه، بعد التحديث أو تسجيل الدخول أو من جهاز آخر، ترى `zeroReview` نفسه.

## المعاينة والإلغاء والتأكيد

المعاينة هي `GET` للحساب أو للقائمة. لا تكتب ولا تعيد ترتيبًا. الإلغاء هو عدم إرسال `POST`؛ لا يوجد مسار إلغاء. التأكيد يرسل النسخة المالية الظاهرة في تلك المعاينة كما هي.

طلب التأكيد:

```json
{ "expectedFinancialVersion": 2 }
```

الرؤوس المطلوبة لكل `POST`، مثل بقية الكتابات: ملف تعريف الارتباط `abdo_session`، و`X-CSRF-Token`، و`X-Client-Api-Version: 1`، و`Content-Type: application/json`. لا يُستخدم `requestId` في هذا المسار.

نجاح أول:

```json
{
  "ok": true,
  "data": {
    "zeroReview": {
      "pending": false,
      "financialVersion": 2,
      "reviewedAt": "2026-11-09T00:40:00.000Z",
      "reviewedByName": "اسم المراجع"
    }
  }
}
```

الحالة `200`. الخادم ينشر حدث القسم: `customer.changed` أو `company.changed` أو `libyan-deposit.changed` أو `egyptian-deposit.changed`، مع `action: "zero_reviewed"`. بعد النجاح تنقل القائمة الكارت إلى المجموعة السفلى لأن رتبته تصبح صفرًا مراجعًا. الرصيد و`version` و`updatedAt` و`summary.totalDebt` و`summary.netBalance` و`summary.activeCards` والسجل لا تتغير. `pendingReviewCount` ينقص واحدًا.

تكرار نفس النسخة بعد النجاح:

```json
{
  "ok": true,
  "data": {
    "zeroReview": {
      "pending": false,
      "financialVersion": 2,
      "reviewedAt": "2026-11-09T00:40:00.000Z",
      "reviewedByName": "اسم المراجع"
    },
    "replayed": true
  }
}
```

`replayed` داخل `data` وليس `meta`. لا يُضاف تدقيق ولا حدث ثان.

## الأخطاء

الغلاف العام:

```json
{
  "ok": false,
  "error": {
    "code": "ZERO_REVIEW_CHANGED",
    "message": "تغيّر الكارت بعد عرضه. راجع آخر حركة قبل تأكيد المراجعة.",
    "correlationId": "..."
  }
}
```

| الحالة | الرمز | متى | هل تُكتب المراجعة؟ |
|---|---|---|---|
| 400 | `INVALID_REVIEW_VERSION` | القيمة ليست عددًا صحيحًا موجبًا أو صفرًا | لا |
| 401 | `AUTH_REQUIRED` | لا جلسة | لا |
| 403 | `CSRF_REJECTED` | رمز CSRF ناقص أو قديم | لا |
| 403 | `PERMISSION_DENIED` | الصلاحية لا تطابق القسم | لا |
| 404 | `NOT_FOUND` | الحساب في قسم آخر أو مؤسسة أخرى أو محذوف أو مرتبط بالنظام | لا |
| 409 | `CLIENT_VERSION_MISMATCH` | رأس الواجهة ليس `1` | لا |
| 409 | `ZERO_REVIEW_CHANGED` | الرصيد لم يعد صفرًا أو النسخة المالية تغيرت | لا |
| 409 | `ZERO_REVIEW_NOT_PENDING` | الرصيد صفر والنسخة مطابقة لكن الكارت لا ينتظر مراجعة | لا |

رسالة النسخة غير الصالحة: `نسخة المراجعة غير صالحة. حدّث الكارت ثم أعد المحاولة.`

رسالة عدم الانتظار: `هذا الكارت لا ينتظر مراجعة تصفير.`

`details.permission` في الرفض يكون `customers.zero_review` للعملاء، أو `companies.write` أو `libyan_deposits.write` أو `egyptian_deposits.write` لبقية الأقسام. `details.entity` في عدم الوجود: `customer` أو `company` أو `libyan_deposit` أو `egyptian_deposit`.

نسخة قديمة، أو رصيد أصبح غير صفري، أو حركة وصلت أثناء انتظار الطلب: الاستجابة `409 ZERO_REVIEW_CHANGED` ويبقى الكارت غير معتمد. الفحص والتحديث داخل `BEGIN IMMEDIATE`، وشرط التحديث نفسه هو الرصيد صفر مع النسخة المالية المرسلة ومع `zero_review_pending=1`. حركة منافسة تُعتمد أولًا تغيّر النسخة، فيفشل التأكيد القديم. إذا اعتُمدت المراجعة أولًا ثم جاءت حركة مالية، فالمحفز يلغي المراجعة ويزيد النسخة.

## الصلاحيات

- العملاء: المدير فقط. `debts.write` لا تكفي. هذا سلوك الخادم القائم ولم يُغيّر.
- الشركات: `companies.write`، والمدير يتجاوز فحص الصلاحية كما في بقية الكتابات.
- الأمانات الليبية: `libyan_deposits.write` أو المدير.
- الأمانات المصرية: `egyptian_deposits.write` أو المدير.
- العرض فقط مرفوض. صلاحية قسم لا تراجع قسمًا آخر.
- إرسال معرف شركة إلى مسار العملاء، أو معرف ليبي إلى مسار الشركات، يرجع `404` ولا يراجع الحساب.

واجهة الموقع تعرض علامة المراجعة للعملاء عند المدير فقط، ولشركات والأمانات عند من يملك كتابة ذلك القسم. العلامة في الموقع ترسل النسخة الحالية مباشرة كما كان زر العملاء. المعاينة ثم الإلغاء سلوك عميل التطبيق: المعاينة `GET`، والإلغاء عدم الإرسال.

## القائمة

`filter=pending-review` يعمل على مسارات القوائم الأربعة ويبقى فعالًا مع `q`. `summary.pendingReviewCount` يحسب القسم كله ويستثني المحذوف والمرتبط بالنظام، ولا يتأثر بالصفحة أو البحث.

ترتيب القائمة: الصفر الذي ينتظر المراجعة يبقى مع الكروت المتحركة في الأعلى، ثم الأصفار المراجعة أو التاريخية في الأسفل. الاسم والتثبيت لا يغيران المراجعة. أي تحديث لـ`current_balance_units` أو `financial_updated_at` يزيد `financialVersion` ويمسح المراجعة، ويعيد الانتظار فقط إذا أصبحت النتيجة صفرًا.

الأصفار الموجودة قبل الترقية 57 تبقى غير منتظرة، مثل أصفار العملاء قبل الترقية 45. الصفر الجديد، أو الذي يبلغ الصفر بحركة لاحقة، هو الذي ينتظر المراجعة.

## الترقية 57 والرجوع

لا أعمدة جديدة ولا إعادة حساب أرصدة. الترقية تستبدل محفزي `customer_zero_review_insert` و`customer_zero_review_financial_change` وفهري `idx_customers_review_feed` و`idx_customers_pending_review`. لم تُنفذ على قاعدة حية.

الرجوع عن الكود يعيد سلوك القراءة القديم ولا يمس الأرصدة. لاستعادة محفزات العملاء فقط بعد الرجوع، تُعاد عبارات الترقية 45 يدويًا؛ لا يشغّل هذا التسليم ذلك الرجوع. الأعلام التي كُتبت بعد 57 تبقى بلا أثر مالي إذا عاد الكود القديم، لأن القراءة القديمة تتجاهل `zeroReview` خارج العملاء.

## دمج عميل Flutter

1. اقرأ `zeroReview` من قائمة القسم أو من `GET /api/{section}/{id}`، واحتفظ بـ`financialVersion` المعروض.
2. أظهر العلامة فقط إذا `balanceUnits === 0` و`zeroReview.pending === true` والمستخدم يملك صلاحية القسم. العملاء للمدير فقط.
3. فتح العلامة يعرض معاينة محلية. الإلغاء لا يرسل طلبًا ولا يعيد الترتيب.
4. التأكيد يرسل `POST` إلى مسار القسم نفسه بالجسم `{ "expectedFinancialVersion": <النسخة المعروضة> }`.
5. عند `200` اعتبر الكارت مراجعًا من رد الخادم، ثم أعد قراءة القائمة. لا تحفظ «تمت المراجعة» محليًا كمصدر حقيقة.
6. عند `409 ZERO_REVIEW_CHANGED` أعد قراءة الكارت واستخدم النسخة الجديدة. لا تضع العلامة كمراجع.
7. عند `403` أخفِ الإجراء لهذا القسم. لا تستخدم مسار العملاء لبقية الأقسام.
