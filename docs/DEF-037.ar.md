# DEF-037 — منع تكرار تقديم التحصيل

الحالة: منفذ ومختبر محليًا. لا تعني هذه الوثيقة نشر الإصلاح على الإنتاج أو staging، ولا اعتماد تطبيق Android ماليًا.

## السلوك

- يتطلب تقديم التحصيل المرتبط بتكليف `requestId` ثابتًا لكل عملية مقصودة.
- يُحفظ الاستلام وإقرار الطلب وبصمته والتدقيق والحدث في معاملة SQLite واحدة؛ فشل أي جزء يلغي العملية كلها.
- إعادة نفس الطلب، بنفس المستخدم والمؤسسة، تسترجع نفس رقم الاستلام والمبلغ دون أحداث أو حركة إضافية، حتى بعد الاعتماد والرفض وإغلاق اليوم وإعادة التشغيل.
- المفتاح نفسه مع تكليف أو مبلغ أو نوع مختلف يرجع `409 REQUEST_ID_REUSED`.
- `status: pending` في الرد المعاد هو إقرار الإنشاء الأصلي؛ الحالة الحالية تؤخذ من `GET /api/collections`.
- الجلسة والصلاحيات وCSRF مطلوبة في كل محاولة. لا تسمح إعادة الطلب بتجاوز سحب الصلاحية.
- يسمح التكليف بدفعات جزئية متعددة قبل الاعتماد؛ كل دفعة جديدة لها مفتاح مستقل. يبقى التحصيل الكلي متوقفًا حتى مراجعة الدفعات المعلقة. لا يؤدي رفض دفعة إلى إخفاء بقية الدفعات المعلقة.
- تستخدم حماية إعادة الإرسال جدول المفاتيح الدائم الموجود. الترحيل 51 يستبدل قيد الاستلام المعلّق الواحد بفهرس يسمح بدفعات جزئية مستقلة، ويحافظ على كل السجلات القائمة.

الواجهة تحفظ المفتاح والمبلغ والنوع والتكليف قبل الإرسال، لكل مستخدم على جهازه. بعد رد مجهول النتيجة، يظهر إجراء «إعادة التحقق من الاستلام السابق» دون إعادة إرسال تلقائية أو تغيير بيانات الطلب. إذا تعذر التخزين المحلي لا يُرسل تحصيل جديد. أثناء استرجاع طلب مجهول، حتى فشل الصلاحيات لا يمسح المفتاح؛ فقد تكون المحاولة الأصلية محفوظة بالفعل. ثُبّت ارتفاع خانة المبلغ لمنع تحرك زر الحفظ عند انتهاء تكبير الخط.

## تحقق القبول

شُغّل الفحص الكامل `npm.cmd run check`: نجح فحص الأنواع وESLint وجميع الاختبارات الـ183. نجح بناء الواجهة والخادم.

تغطي الاختبارات المخصصة غياب المفتاح، وتغيير المحتوى، وعزل المستخدم والمؤسسة، وسحب الصلاحيات، والطلب المتزامن، والتراجع عند فشل حفظ الإقرار، واسترجاع الإقرار بعد إغلاق اليوم وإعادة فتح قاعدة البيانات والصيانة.

تشمل أيضًا ترقية قاعدة مخططها 50 دون حذف بيانات، وتقديم ثلاث دفعات جزئية 30 و30 و40 قبل الاعتماد، ثم اعتمادها بترتيب مختلف لتصبح دفعات الحساب الثلاث فقط والرصيد صفرًا. اختُبر رفض واحدة مع إبقاء بقية الدفعات ظاهرة. وفي المتصفح قُدمت ثلاث دفعات جزئية على مقاس الهاتف قبل اعتماد أي منها، ثم ظهرت للإدارة واعتمدتها كلًا على حدة مع التحقق من الرصيد النهائي.

في اختبار المتصفح، أُرسل الطلب إلى خادم اختبار بقاعدة بيانات مصطنعة، ثم حُجب الرد بعد حفظه فعليًا. اعتمد المدير التحصيل، ثم أُعيد فتح الصفحة وأُرسلت محاولة الاسترجاع بنفس المفتاح. النتيجة: استلام واحد، وحركة دفع واحدة، ورصيد 70 من أصل 100 بعد دفع 30. كما تحقق الاختبار من رفض تغيير المبلغ أثناء الغموض، والاحتفاظ بالمفتاح عند سحب الصلاحية، ومنع الإرسال عند تعطل التخزين، والحفظ بالماوس على شاشة هاتف مع تكبير الخط الكبير. اجتاز اختبار العرض الحالي للتحصيلات أيضًا.

أوامر إعادة التحقق:

```powershell
npm.cmd run check
npm.cmd run build
npm.cmd run test:collection-idempotency-ui
npm.cmd run test:collections-ui
```

## تسليم التكامل والنشر

تفاصيل العقد والأمثلة والأخطاء في [API.md](../API.md). يجب أن يُحدّث Android بيانات الطلب ليُنشئ المفتاح قبل الإرسال ويحفظ نفس المحتوى عبر إعادة المحاولة وإعادة فتح التطبيق. يلزم نشر الخادم والواجهة المتوافقين معًا؛ الطلب بلا مفتاح سيُرفض. لا تُعاد المحاولات السابقة للإصلاح بمفاتيح جديدة قبل مراجعة السجلات. يلزم إعادة اختبار التطبيق على إصدار staging المنشور قبل إغلاق العيب في سجل قبول التطبيق.

الحماية تخص إعادة نفس العملية بمفتاحها؛ استعمال مفاتيح مختلفة لا يُثبت أنها نفس العملية. لم تتغير سياسة الدفع الزائد أو العملات أو التقريب، ولم يُنفذ DEF-035 ضمن هذا الإصلاح. مسار الاستلام غير المرتبط بعميل له حماية منفصلة ولم يُعدّل هنا.
